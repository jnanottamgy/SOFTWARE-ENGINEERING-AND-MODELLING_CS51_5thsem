Q1 Differentiate between functional and non-functional requirements with examples.

5 marksCO2L2Very likely
Definitions 1 + Comparison table 2 + Examples 2
Model answer

Functional requirements (FRs) are statements of services the system should provide, how the system should react to particular inputs and how the system should behave in particular situations. They may also state what the system should not do.

Non-functional requirements (NFRs) are constraints on the services or functions offered by the system, such as timing constraints, constraints on the development process and standards. They often apply to the system as a whole rather than to individual features or services.

  • The line is not sharp: a security NFR (only authorised users may access the system) generates FRs such as user authentication.
  • Two levels: both are written as user requirements (natural language + diagrams, for customers) and system requirements (detailed and structured, for developers; may be part of the contract).
  • Imprecision: FRs must be precise — "search" may mean all clinics (user) or one clinic (developer's simpler reading), causing delays and cost.

Give one FR and one NFR from the same system, and label each NFR with its type (product, organisational or external). That shows the examiner you know the classification too.

Q2 What are non-functional requirements? List the types of non-functional requirements. What are the metrics for specifying non-functional requirements?

5 marksCO2L2Asked in CIE-1 2024Very likely
Definition 1 + Types with diagram 2 + Metrics 2
Model answer

Non-functional requirements are constraints on the services or functions offered by the system, such as timing constraints, constraints on the development process and standards. They define system properties and constraints (e.g. reliability, response time, storage requirements) and often apply to the system as a whole. They may be more critical than functional requirements: if they are not met, the system may be useless.

Types of NFRs (classified by where they come from):

  1. Product requirements — specify that the delivered product must behave in a particular way (run-time behaviour): usability, efficiency (performance, space), dependability, security. E.g. Mentcare shall be available to all clinics Mon–Fri, 08:30–17:30.
  2. Organisational requirements — a consequence of organisational policies and procedures: environmental, operational, development (programming language, development environment, process standards). E.g. users shall authenticate with their health authority identity card.
  3. External requirements — arise from factors external to the system and its development process: regulatory, ethical, legislative (accounting, safety/security). E.g. the system shall implement the patient privacy provisions in HStan-03-2006-priv.

Metrics. A vague goal ("easy to use") cannot be tested, so NFRs should be written as verifiable requirements — statements using some measure that can be objectively tested. The metrics are:

PropertyMeasure
SpeedProcessed transactions/second · User/event response time · Screen refresh time
SizeMbytes · Number of ROM chips
Ease of useTraining time · Number of help frames
ReliabilityMean time to failure · Probability of unavailability · Rate of failure occurrence · Availability
RobustnessTime to restart after failure · Percentage of events causing failure · Probability of data corruption on failure
PortabilityPercentage of target dependent statements · Number of target systems

Example: the goal "the system should be easy to use by medical staff" becomes the testable NFR "Medical staff shall be able to use all the system functions after four hours of training; after this, the average number of errors made by experienced users shall not exceed two per hour of system use."

Types — P-O-E: Product → U Eat Dosa Slowly (Usability, Efficiency, Dependability, Security) · Organisational → Every Office Decides (Environmental, Operational, Development) · External → the REaL world (Regulatory, Ethical, Legislative).
Metrics — "Six Smart Engineers Rarely Run Poorly": Speed, Size, Ease of use, Reliability, Robustness, Portability.

Q3 Explain the requirements engineering process with a neat labelled spiral diagram.

5 marksCO2L2Asked in CIE-1 2024Very likely
Activities 1 + Spiral diagram 2 + Explanation 2
Model answer

Requirements engineering (RE) is the process of establishing the services that a customer requires from a system and the constraints under which it operates and is developed. It has three key activities — requirements elicitation and analysis (discovering requirements by interacting with stakeholders), requirements specification (converting them into a standard form) and requirements validation (checking that they define the system the customer wants) — plus requirements management to handle change. In practice these activities are interleaved and organised as an iterative process around a spiral.

  1. Three sectors: every loop of the spiral passes through elicitation → specification → validation.
  2. More detail each loop: inner loop — business requirements specification and feasibility study; middle loop — user requirements elicitation and specification, checked by prototyping; outer loop — system requirements elicitation, specification and modeling, checked by reviews.
  3. Effort varies: the time spent on each activity depends on the stage of the process, the type of system and the budget. Early on, effort goes on high-level business and non-functional requirements and user requirements; later, on detailed system requirements.
  4. Number of loops can vary: the spiral can be exited after some or all user requirements are elicited; agile development can be used instead of prototyping, so requirements and implementation are developed together.
  5. Output: the system requirements document.
  6. Change: in virtually all systems requirements change, so requirements management runs alongside the spiral.

Draw a "Y" (three lines from a centre); label specification (top), elicitation (left), validation (right); draw the spiral outwards from Start and write the nine activities in order — business req. spec → feasibility study → user req. elicitation → user req. spec → prototyping → system req. elicitation → system req. spec & modeling → reviews — ending in the system requirements document.

Q4 Explain the requirements elicitation and analysis process with a neat diagram. Briefly explain interviewing and ethnography.

5 marksCO2L2Very likely
Diagram 1.5 + Four activities 1.5 + Interviewing 1 + Ethnography 1
Model answer

Requirements elicitation and analysis involves technical staff working with customers to find out about the application domain, the services that the system should provide and the system's operational constraints. It may involve end-users, managers, engineers involved in maintenance, domain experts, trade unions, etc. — the stakeholders.

  1. Requirements discovery — interacting with stakeholders to discover their requirements; domain requirements are also discovered here.
  2. Requirements classification and organisation — takes the unstructured collection of requirements, groups related requirements and organises them into coherent clusters.
  3. Prioritisation and negotiation — prioritising requirements and resolving requirements conflicts through negotiation between stakeholders.
  4. Requirements specification — requirements are documented and input into the next round of the spiral.

The process is iterative, with continual feedback between activities; the analyst's understanding improves with each round.

Interviewing

Formal or informal interviews in which the RE team asks stakeholders about the system they use now and the system to be developed.

  • Closed interviews — based on a pre-determined list of questions.
  • Open interviews — no predefined agenda; various issues are explored with stakeholders.

In practice a mix of both. The interviewer must be open-minded and prompt discussion with a springboard question, a requirements proposal or a prototype. Weak for domain requirements (jargon; knowledge too familiar to articulate).

Ethnography

An observational technique: a social scientist spends a considerable time observing and analysing how people actually work. People do not have to explain their work, and social and organisational factors can be observed. It finds requirements from how people actually work and from cooperation and awareness of others' activities, but cannot identify new features.

Focused ethnography (developed in an air traffic control project) combines ethnography with prototyping: prototype development raises unanswered questions that focus the ethnographic analysis.

The four activities in order — D-C-P-S: "Doctors Collect, Prioritise, Sign" (Discovery, Classification & organisation, Prioritisation & negotiation, Specification).

Q5 Explain the structure of the IEEE software requirements specification (requirements document).

5 marksCO2L2Asked in CIE-1 2024Very likely
Definition 1 + Chapter structure 3 + Users & notes 1
Model answer

The software requirements document (software requirements specification, SRS) is the official statement of what is required of the system developers. It includes both a definition of user requirements and a specification of the system requirements. It is not a design document: it sets out what the system should do rather than how. One possible structure, based on the IEEE standard, is:

#ChapterDescription
1PrefaceDefines the expected readership; version history, with a rationale for each new version and a summary of changes.
2IntroductionDescribes the need for the system, briefly its functions and how it works with other systems, and how it fits the organisation's business or strategic objectives.
3GlossaryDefines the technical terms used; makes no assumptions about the reader's experience or expertise.
4User requirements definitionServices provided for the user, and the non-functional requirements, in natural language and diagrams customers understand; product and process standards to be followed.
5System architectureHigh-level overview of the anticipated architecture, showing the distribution of functions across system modules; reused components are highlighted.
6System requirements specificationFunctional and non-functional requirements in more detail; interfaces to other systems may be defined.
7System modelsGraphical models showing relationships between system components and between the system and its environment (object, data-flow, semantic data models).
8System evolutionFundamental assumptions on which the system is based, and anticipated changes due to hardware evolution, changing user needs, etc.
9AppendicesDetailed application-specific information, e.g. hardware requirements (minimal and optimal configurations) and database requirements (logical organisation of data).
10IndexA normal alphabetic index, plus indexes of diagrams, functions, and so on.

Users of the document — it is organised so that both customers and developers can use it:

Variability: the information included depends on the type of system and the approach to development. Incrementally developed systems have less detail; critical and outsourced systems need detailed, precise specifications. The IEEE standard is mostly applicable to large systems engineering projects.

"PIG-U, four S's, A-I": Preface, Introduction, Glossary, User requirements definition → System architecture, System requirements specification, System models, System evolution → Appendices, Index.

Q6 What is requirements validation? Explain the requirements checks and validation techniques.

5 marksCO2L2Likely
Definition 1 + Five checks 2 + Techniques & reviews 2
Model answer

Requirements validation is the process of demonstrating that the requirements define the system that the customer really wants. It overlaps with elicitation and analysis, as it is concerned with finding problems with the requirements. It is important because requirements error costs are high: fixing a requirements error after delivery may cost up to 100 times the cost of fixing an implementation error, since the design and implementation must also change and the system must be retested.

Requirements checks

CheckQuestion asked
1. ValidityDoes the system provide the functions which best support the customer's needs?
2. ConsistencyAre there any requirements conflicts (contradictory constraints, different descriptions of the same function)?
3. CompletenessAre all functions required by the customer included?
4. RealismCan the requirements be implemented given the available budget and technology?
5. VerifiabilityCan the requirements be checked (can tests show the delivered system meets each one)?

Requirements validation techniques

  1. Requirements reviews — systematic manual analysis of the requirements by a team of reviewers, who check for errors and inconsistencies.
  2. Prototyping — using an executable model of the system to check requirements; end-users and customers experiment with it and feed back requirements changes.
  3. Test-case generation — developing tests for requirements to check testability. If a test is difficult or impossible to design, the requirement will be hard to implement and should be reconsidered.

Requirements reviews

Regular reviews should be held while the requirements definition is being formulated. Both client and contractor staff should be involved. Reviews may be formal (with completed documents) or informal; good communication between developers, customers and users can resolve problems at an early stage. Review checks:

Review checkQuestion
VerifiabilityIs the requirement realistically testable?
ComprehensibilityIs the requirement properly understood?
TraceabilityIs the origin of the requirement clearly stated?
AdaptabilityCan the requirement be changed without a large impact on other requirements?

Checks — V-C-C-R-V: "Very Careful Clients Request Verification" (Validity, Consistency, Completeness, Realism, Verifiability). Techniques — R-P-T: Reviews, Prototyping, Test cases. Do not mix the 5 checks with the 4 review checks; only verifiability is in both.

Q7 Explain the following design concepts: abstraction, modularity, information hiding and functional independence (cohesion and coupling).

5 marksCO2L2Very likely
Abstraction 1 + Modularity with graph 1.5 + Information hiding 1 + Functional independence 1.5
Model answer

1. Abstraction. A modular solution can be stated at many levels of abstraction: at the highest level in broad terms using the language of the problem environment; at lower levels in more detail, using implementation-oriented terms; at the lowest level in a form that can be directly implemented.

  • Procedural abstraction — a sequence of instructions that have a specific and limited function; the name implies the function but specific details are suppressed. E.g. "open" a door (walk to the door, grasp the knob, turn and pull…).
  • Data abstraction — a named collection of data that describes a data object. E.g. "door": door type, swing direction, opening mechanism, weight, dimensions.

2. Modularity. Software is divided into separately named and addressable components, called modules, that are integrated to satisfy problem requirements. "Modularity is the single attribute of software that allows a program to be intellectually manageable" (Myers). But modules should not be split indefinitely:

As the number of modules grows, the cost per module falls but the cost to integrate rises. Total cost is lowest near some number M, so we modularize but stay near M — avoid under-modularity and over-modularity.

3. Information hiding (Parnas). Modules should be "characterized by design decisions that (each) hides from all others": the information (algorithms and data) inside a module is inaccessible to other modules that have no need for it. Modules communicate only the information necessary, through an interface. Benefit: during testing and maintenance, errors introduced by a modification are less likely to propagate to other parts of the software.

4. Functional independence is achieved by developing modules with a "single-minded" function and an "aversion" to excessive interaction with other modules: each module addresses a specific subset of requirements and has a simple interface. Such modules are easier to develop, test and maintain, and errors propagate less. It is assessed by two criteria:

  • Cohesion — an indication of the relative functional strength of a module. A cohesive module performs a single task and ideally does just one thing. Aim: high cohesion.
  • Coupling — an indication of the relative interdependence among modules; it depends on interface complexity, the point at which entry or reference is made, and what data pass across the interface. Aim: low coupling, which avoids the "ripple effect" of errors.

Co-HE-sion = inside one module; COUPLE-ing = between two. Good design = high cohesion, low coupling — "strong teams, few meetings".

Q8 Explain how the requirements model is translated into the design model, and describe the elements of the design model.

5 marksCO2L2Likely
Translation diagram 2 + Explanation 1 + Elements 2
Model answer

Design is the last software engineering action within the modeling activity and sets the stage for construction. The requirements model — its scenario-based, class-based, flow-oriented and behavioural elements — feeds the design task. Using design notation and methods, design produces the design model: a representation of the software that gives detail about the architecture, data structures, interfaces and components needed to implement the system.

  • Data/class design — transforms class models into design class realizations and the data structures needed for implementation (from CRC objects, class attributes).
  • Architectural design — defines the relationships between major structural elements, the architectural styles and design patterns, and the constraints on implementation.
  • Interface design — how the software communicates with interoperating systems and with the humans who use it (from usage scenarios and behavioural models).
  • Component-level design — transforms structural elements of the architecture into a procedural description of software components.

Design should begin with data, the foundation (base of the pyramid); then the architecture is derived. The design model has two dimensions: the process dimension (how the model evolves as design tasks are done) and the abstraction dimension (level of detail).

Elements of the design model

  1. Data design elements — (data architecting) a high-level model of data refined into implementation-specific representations: data structures (component level), a database (application level), a data warehouse (business level).
  2. Architectural design elements — like the floor plan of a house: an overall view of the software as a set of interconnected subsystems, derived from the application domain, requirements model elements and available architectural styles and patterns.
  3. Interface design elements — like the doors, windows and external utilities: how information flows into and out of the system and among its components; three parts — user interface, external interfaces, internal interfaces.
  4. Component-level design elements — like the detailed drawing of each room: the internal detail of each component — data structures, algorithmic detail and an interface to its operations (UML component and activity diagrams, pseudocode).
  5. Deployment-level design elements — how software functionality and subsystems are allocated within the physical computing environment (UML deployment diagram, first in descriptor form, later in instance form).

Write all five elements (the textbook counts four in some places). Draw the pyramid with data/class design at the base — it is the foundation for everything above it.
