Q1 What is software architecture design? What views or perspectives are useful when designing and documenting a system's architecture?

5 marksCO3L2Asked in CIE-1 2024Very likely
Definition + 3 points 2 + Diagram 1 + Views 2
Model answer

Architectural design — is concerned with understanding how a software system should be organized and designing the overall structure of that system.

  1. Overall organization — the software architecture shows the main components (sub-systems) of a system and the relationships between them.
  2. Critical link — it is the first stage of the software design process and the critical link between design and requirements engineering, because it identifies the main structural components in a system and the relationships between them.
  3. Output — an architectural model that describes how the system is organized as a set of communicating components. The architecture is the dominant influence on non-functional characteristics such as performance, robustness, distributability and maintainability.

Views. Each architectural model shows only one view or perspective of the system: how it is decomposed into modules, how the run-time processes interact, or how components are distributed across a network. So, for both design and documentation, we present multiple views. Krutchen's 4+1 view model gives four fundamental views, linked by use cases or scenarios:

  1. Logical view — the key abstractions in the system as objects or object classes; requirements can be related to its entities.
  2. Process view — how, at run-time, the system is composed of interacting processes; useful for judging non-functional characteristics such as performance and availability.
  3. Development view — how the software is decomposed for development into components implemented by a single developer or team; useful for software managers and programmers.
  4. Physical view — the system hardware and how software components are distributed across the processors; useful for systems engineers planning a deployment.

+1 Use cases or scenarios relate the four views to each other. Hofmeister et al. add a conceptual view (an abstract view, e.g. the packing robot diagram). In practice it is rarely necessary to describe all perspectives: develop the views that are useful for communication.

Asked as Q1(c) in 2024. Both halves carry marks: definition + 3 points first, then the 4+1 sketch and one line per view. Use the exact view names: logical, process, development, physical, +1 scenarios.

Q2 Explain Krutchen's 4+1 view model of software architecture with a neat diagram.

5 marksCO3L2Very likely
Diagram 2 + Four views 2 + Scenarios (+1) 1
Model answer

No single diagram can show everything about a system: each architectural model shows only one view or perspective. In his well-known 4+1 view model of software architecture, Krutchen suggests four fundamental architectural views, which are related using common use cases or scenarios (the "+1").

ViewWhat it showsUseful forExample: Mentcare (illustration)
1. LogicalThe key abstractions in the system as objects or object classes. It should be possible to relate the system requirements to entities in this view.Relating requirements to the designClasses such as Patient, Consultation, Prescription, Clinic.
2. ProcessHow, at run-time, the system is composed of interacting processes.Judging performance, availability and other non-functional characteristicsA client process on each clinic PC talks to a server process that handles patient-record requests.
3. DevelopmentHow the software is decomposed for development: its breakdown into components implemented by a single developer or development team.Software managers and programmersModules for patient records, appointments and prescribing, each given to one team.
4. PhysicalThe system hardware and how software components are distributed across the processors in the system.Systems engineers planning a system deploymentClinic PCs connected over the network to a central database server.

+1 Use cases or scenarios. A scenario describes one typical interaction with the system, e.g. "a doctor records a consultation". Tracing the same scenario through all four views links the views and checks that they fit together.

In practice, conceptual views are almost always developed during design; other views are added as different aspects are discussed. It is rarely necessary to describe the system from all perspectives: except for critical systems, develop only the views that are useful for communication.

Don't mix up the pairs: process view (run-time processes) ≠ development view (code split among teams); physical view (hardware) ≠ logical view (classes). The +1 links the four views; it is not a fifth view.

Q3 What are architectural design decisions? Explain the fundamental questions an architect must answer during architectural design.

5 marksCO3L2Very likely
Creative process 1 + Eight questions (diagram) 3 + Notes 1
Model answer

Architectural design is a creative process in which you design a system organization that will satisfy the functional and non-functional requirements of a system.

  1. No formulaic process — the process differs depending on the type of system being developed, the background and experience of the system architect, and the specific requirements for the system.
  2. A series of decisions — so it is best to think of architectural design as a series of decisions to be made rather than a sequence of activities.
  3. Common decisions — a number of common decisions span all design processes, and they affect the non-functional characteristics of the system. Based on their knowledge and experience, architects answer eight fundamental questions:
  • Distribution (2) — embedded systems and apps for PCs and mobiles need not be distributed, but most large systems are; the choice of distribution architecture is a key decision that affects performance and reliability.
  • Structure, decomposition, control (4–6) — together these form the architectural style (Garlan and Shaw): choose a structure such as client–server or layered, decide how to decompose components into sub-components, and in control modelling decide how the execution of components is controlled.
  • Evaluation — the true test is how well the system meets its requirements when in use; before that, compare the design with reference architectures or generic patterns.

Generic · Distribution · Patterns · Structure · Decomposition · Control · Non-functional · Documentation: "Good Developers Prefer Simple Designs; Clear Non-functional Docs".

Q4 Explain how architectural design depends on the non-functional requirements of a system (performance, security, safety, availability, maintainability).

5 marksCO3L2Very likely
Why NFRs drive the architecture 1 + Five strategies 3 + Conflict 1
Model answer

Software architecture affects the performance, robustness, distributability and maintainability of a system (Bosch). Individual components implement the functional requirements, but the dominant influence on the non-functional characteristics is the system's architecture; non-functional requirements have the most significant effect on the architecture (Chen et al.). Therefore the choice of architectural style and structure should depend on the non-functional requirements:

If this is critical……use this architectural strategyWhy it works
1. PerformanceLocalise critical operations and minimise communications. Use large rather than fine-grain components.Critical operations sit in a few components on the same computer, so most interactions happen inside a component. Replicating the system on different processors may also help.
2. SecurityUse a layered architecture with the critical assets in the inner layers.The most critical assets are protected by the innermost layers, with a high level of security validation applied to them.
3. SafetyLocalise safety-critical features in a small number of sub-systems.Reduces the cost of safety validation and may allow a protection system that safely shuts the system down on failure.
4. AvailabilityInclude redundant components and mechanisms for fault tolerance.Components can be replaced and updated without stopping the system; the system keeps working when a part fails.
5. MaintainabilityUse fine-grain, replaceable components.Small, self-contained components can readily be changed. Separate producers of data from consumers; avoid shared data structures.

Conflicts and trade-offs. There is potential conflict between some of these architectures. Performance wants a few large components, while maintainability wants many small, fine-grain components. If both are important, a compromise is found by using different architectural patterns or styles for separate parts of the system. Security is now almost always a critical requirement, so the architecture must maintain security while also satisfying the other non-functional requirements.

Example. In Mentcare, patient records are the critical asset, so they sit in the innermost layer; in the insulin pump, the safety-critical dose computation and checks are co-located in one small component that can be validated thoroughly.

Learn the five rows as keyword pairs: Performance → large, Security → layers, Safety → localise, Availability → redundancy, Maintainability → fine-grain. End with the performance vs maintainability conflict: it lifts a 4/5 answer to 5/5.

Q5 What are the advantages of designing and documenting the software architecture explicitly? Differentiate architecture in the small and architecture in the large.

5 marksCO3L1 / L2Likely
Three advantages 3 + Small vs large 2
Model answer

(a) Advantages. "Explicit" means the architecture is deliberately designed and written down, not left to emerge by accident. Bass, Clements and Kazman suggest that explicitly designing and documenting a software architecture has three advantages:

  1. Stakeholder communication — the architecture is a high-level presentation of the system that may be used as a focus of discussion by a range of different stakeholders (users, customers, managers, engineers).
  2. System analysis — making the architecture explicit at an early stage requires some analysis, so we can check whether the system can meet its non-functional requirements. Architectural decisions have a profound effect on whether critical requirements such as performance, reliability and maintainability can be met.
  3. Large-scale reuse — an architectural model is a compact, manageable description of how a system is organized and how its components interoperate. Systems with similar requirements often have the same architecture, so it may be reused across a range of systems; product-line architectures may be developed.

(b) Architecture in the small vs architecture in the large.

PointArchitecture in the smallArchitecture in the large
Concerned withThe architecture of individual programs.The architecture of complex enterprise systems that include other systems, programs and program components.
Main questionHow an individual program is decomposed into components.How many separate systems, programs and components are organized together.
Distribution and ownershipA single program.May be distributed over different computers, which may be owned and managed by different companies.
Example (illustration)One program split into user interface, calculations and data storage components.Order and stock systems of one company linked to the payment and delivery systems of another.

Advantages = CAR: Communication (with stakeholders), Analysis (of the system), Reuse (large-scale). Small = one program; large = an enterprise of systems.

Q6 What are box-and-line diagrams? Explain the two ways in which architectural models are used.

5 marksCO3L2Likely
Definition + strengths 1 + Criticism 1 + Two uses 2 + When rigorous 1
Model answer

Box-and-line (block) diagrams are simple, informal diagrams in which boxes represent components (entities) and lines or arrows show the relationships between them, e.g. the packing robot architecture. They are the most frequently used method for documenting software architectures.

  1. Simple and informal — quick to draw, even on a whiteboard.
  2. Intuitive — people from different disciplines (domain experts and engineers) can readily understand them and join the discussion.
  3. Not cluttered with detail — they show the whole system, so they are useful for communication with stakeholders and for project planning.

Criticism. Bass et al. criticise them because they lack semantics (precise meaning) and are very abstract: they do not show the types of relationships between components, nor the externally visible properties of the entities or sub-systems.

Two uses of architectural models. Whether the criticism matters depends on how the model is used; this explains why industry uses block diagrams although theory criticises them.

1. To facilitate discussion about the system design2. To document an architecture that has been designed
AimA high-level architectural view that is not cluttered with detail.A complete system model showing the components, their interfaces and their connections.
BenefitStakeholders can relate to it and discuss the system as a whole; it identifies key components, so managers can assign people and plan development.A detailed description makes the system easier to understand and evolve.
NotationInformal block diagrams are enough.Ideally a more rigorous notation, e.g. an ADL.

When is rigour worth it? A detailed, complete description leaves less scope for misunderstanding the relationships between components, but it is expensive and time-consuming to develop and it is hard to know whether it is cost-effective, so it is not widely used. It is mainly worthwhile for critical systems; otherwise, informal models useful for communication are enough.

Write the key sentence: "the requirements for model semantics depend on how the models are used". It resolves the contradiction and earns the last mark.

Q7 Explain architectural design with the example of the packing robot control system. Why must the architecture be designed early, even in agile development? Mention architecture reuse.

5 marksCO3L2Likely
Diagram 2 + Explanation 1 + Agility 1 + Reuse 1
Model answer

Architectural design identifies the main structural components of a system and the relationships between them. Sommerville's example is a packing robot that can pack different kinds of objects. It uses a vision component to pick out objects on a conveyor, identify the type of object and select the right kind of packaging. It then moves objects from the delivery conveyor to be packaged and places packaged objects on another conveyor.

How to read it. This is an abstract block (box-and-line) diagram, a conceptual view of the system:

  • Boxes represent components, e.g. the vision system and the conveyor controller.
  • Boxes within boxes show a component decomposed into sub-components: arm + gripper controllers form one sub-system; packaging selection + packing systems form another.
  • Arrows mean that data and/or control signals pass from component to component in the direction of the arrow.

Agility and architecture. It is generally accepted that an early stage of agile processes is to design an overall system architecture; incremental development of architectures is not usually successful. Refactoring individual components in response to change is relatively easy, but refactoring the architecture is expensive, because it affects so many components: most of them would have to be modified to adapt to the change.

Architecture reuse. Each system is unique, but architectures are often reused:

  1. Same domain — systems in the same application domain often have similar architectures that reflect domain concepts.
  2. Product lines — application product lines are built around a core architecture with variants that satisfy particular customer requirements.
  3. Patterns or styles — the architecture may be designed around one or more architectural patterns or styles, which capture the essence of an architecture and can be instantiated in different ways.

Backup questions (prepare if you have time)

5M
How should architectural views be represented? Compare the UML, ADLs and informal notations.
UML: some argue it suits architecture; Sommerville disagrees (no abstractions for high-level description; object classes are too close to the implementation), so it is best for detailed documentation or model-driven development. ADLs: components and connectors with rules for well-formed architectures; precise but specialist, not widely used. Informal notations: quick, easy, the most common; except for critical systems, develop only the views useful for communication. Revise 6.10.
2M
What is a conceptual view? Give an example.
Hofmeister et al.: an abstract view that can (1) be the basis for decomposing high-level requirements into detailed specifications, (2) help decide which components can be reused, (3) represent a product line rather than a single system. Example: the packing robot (Fig Q7). Almost always developed during design. Revise 6.9.
2M
Define an architectural pattern (style).
A description of a system organization, such as a client–server organization or a layered architecture; it captures the essence of an architecture that has been used in different software systems. "Pattern" and "style" mean the same thing. (The patterns themselves are studied after CIE-1.) Revise 6.7.
5M
Why is architectural design called the critical link between requirements engineering and design?
Definition → it is the first stage of design and identifies the main structural components and their relationships → output: an architectural model of communicating components → requirements and architecture overlap: an abstract architecture grouping functions into large-scale sub-systems is used to discuss requirements with stakeholders.
