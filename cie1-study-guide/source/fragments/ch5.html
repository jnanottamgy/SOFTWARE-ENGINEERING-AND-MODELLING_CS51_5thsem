5.1 Design within the context of software engineering Must know

What is software design? Must know

Requirements say what the system must do. Design decides how it will be built — its parts, how they connect, what data they keep, how users and other systems talk to it. It is the architect's blueprint that programmers follow.

Software design covers the set of principles, concepts and practices that lead to a high-quality system or product. Principles give the overall philosophy; concepts must be understood before design practice is applied; practice creates representations of the software that guide construction (coding and testing).

Design model — a representation of the software that gives detail about the software architecture, data structures, interfaces and components needed to implement the system. (The requirements model describes the required data, function and behaviour.)

Who / why?
Software engineers do it. The design can be assessed for quality and improved before code is written and tested — design is where software quality is established.
Steps
Represent the architecture → model the interfaces (to users, other systems/devices, and between its own components) → design the components. All follow the basic design concepts.
Work product
A design model with architectural, interface, component-level and deployment representations.
Check
The team reviews it for errors, inconsistencies and omissions, better alternatives, and whether it can be built within constraints, schedule and cost.

Firmness, commodity and delight. Vitruvius said good buildings show these three; so should good software — firmness: no bugs that inhibit its function; commodity: suitable for the purpose intended; delight: pleasurable to use. Designers reach such a model by diversification (collecting a repertoire of alternatives — components, solutions, knowledge) and then convergence (choosing the elements that meet the requirements and rejecting the rest until one configuration remains).

Where design sits Must know

Design is the technical kernel of software engineering and is applied whatever process model is used. It begins once requirements have been analysed and modelled; it is the last software engineering action within the modeling activity and sets the stage for construction (code generation and testing).

Translating the requirements model into the design model Must know

The requirements model — its scenario-based, class-based, flow-oriented and behavioural elements — feeds the design task. Using design notation and methods, design produces the four design models: a data/class design, an architectural design, an interface design and a component-level design.

Design modelWhat it definesMain input
Data/class designTransforms class models into design class realizations and the data structures needed for implementation (partly with the architecture; more detail as each component is designed).CRC objects and relationships; class attributes
Architectural designThe relationships between major structural elements, the architectural styles and design patterns that meet the requirements, and the constraints on implementation — the "framework" of the system.The requirements model
Interface designHow the software communicates with interoperating systems and with the humans who use it. An interface implies a flow of information (data and/or control) and a specific behaviour.Usage scenarios, behavioural models
Component-level designTransforms structural elements of the architecture into a procedural description of software components.Class-based, flow and behavioural models

Design should always begin with data — the foundation for all other elements (the base of the pyramid). Then the architecture is derived; only then are the other design tasks done.

Why is design important? Quality Must know

Importance of design — in one word, quality: design is the place where quality is fostered in software engineering.

  1. Design gives representations of software that can be assessed for quality.
  2. It is the only way to accurately translate stakeholders' requirements into a finished product.
  3. It is the foundation for all the software engineering and support activities that follow.
  4. Without design the system may be unstable — it fails when small changes are made, is difficult to test, and its quality cannot be assessed until late, when time is short and money is spent.

Design vs coding (SafeHome): code is just the language used to represent a design. A programming language shows details (data structures, algorithms) well but not architecture or component collaboration — "a screwed-up architecture can ruin even the best code". The difference is the level of abstraction.

5.2 The design process Important

Design is an iterative process that translates requirements into a "blueprint" for constructing the software. The first blueprint is holistic — at a high level of abstraction, traceable directly to the system objective and to the data, functional and behavioural requirements. Each iteration refines it to lower levels of abstraction, still traceable to requirements but more subtly.

Three characteristics of a good design Must know

McGlaughlin's three characteristics guide the evaluation of a design (each is also a goal of the design process):

  1. It must implement all the explicit requirements of the requirements model and accommodate all the implicit requirements desired by stakeholders.
  2. It must be a readable, understandable guide for those who generate code and those who test and support the software.
  3. It should give a complete picture of the software, addressing the data, functional and behavioural domains from an implementation perspective.

Quality guidelines Important

  1. A design should exhibit an architecture that (a) uses recognizable architectural styles or patterns, (b) is made of components with good design characteristics, and (c) can be implemented in an evolutionary fashion (small systems may be designed linearly).
  2. A design should be modular — logically partitioned into elements or subsystems.
  3. It should contain distinct representations of data, architecture, interfaces and components.
  4. It should lead to data structures appropriate for the classes, drawn from recognizable data patterns.
  5. It should lead to components with independent functional characteristics.
  6. It should lead to interfaces that reduce the complexity of connections between components and with the environment.
  7. It should be derived using a repeatable method driven by information from requirements analysis.
  8. It should use a notation that effectively communicates its meaning.

These come from fundamental design principles, systematic methodology and thorough review. During design there is no code to test, so quality is checked by technical reviews: a meeting of two to four people — a review leader (plans and runs it), a recorder (takes notes) and the producer (whose work is reviewed) — who read the design beforehand and list errors, omissions and ambiguities (typically 90 minutes to 2 hours).

FURPS quality attributes Must know

Hewlett-Packard's FURPS attributes are a target for all software design:

AttributeAssessed / measured by
FunctionalityThe feature set and capabilities of the program, the generality of the functions delivered, and the security of the overall system.
UsabilityHuman factors, overall aesthetics, consistency and documentation.
ReliabilityFrequency and severity of failure, accuracy of output, mean-time-to-failure (MTTF), ability to recover from failure, and predictability.
PerformanceProcessing speed, response time, resource consumption, throughput and efficiency.
SupportabilityExtensibility, adaptability, serviceability (together = maintainability) plus testability, compatibility, configurability, ease of installation and ease of localizing problems.

The attributes are not weighted equally (one system stresses functionality/security, another performance, another reliability), but all must be considered as design begins, not after construction starts.

FURPS — "Fast Users Rarely Pick Slow apps". Supportability hides maintainability (extensibility + adaptability + serviceability).

Evolution of design and common features of design methods Important

Evolution (about six decades): modular programs and top-down refinement → structured programming → translating data flow or data structure into a design → object-oriented design → software architecture and design patterns → aspect-oriented methods, model-driven and test-driven development.

All design methods share four characteristics: (1) a mechanism for translating the requirements model into a design representation; (2) a notation for functional components and their interfaces; (3) heuristics for refinement and partitioning; (4) guidelines for quality assessment.

Generic task set for design Important

  1. Design data structures for the data objects and attributes in the information domain model.
  2. Select an architectural style appropriate for the software.
  3. Partition the analysis model into design subsystems and allocate them in the architecture (each subsystem functionally cohesive; design subsystem interfaces; allocate analysis classes or functions).
  4. Create design classes or components: translate analysis classes into design classes; check against design criteria and inheritance; define methods and messages; select design patterns; review and revise.
  5. Design interfaces to external systems or devices.
  6. Design the user interface: review task analysis; specify action sequences from scenarios; build a behavioural model; define interface objects and control mechanisms; review.
  7. Conduct component-level design: specify algorithms at a low level of abstraction; refine each interface; define component data structures; review and correct errors.
  8. Develop a deployment model.

5.3 Design concepts Must know

A set of fundamental design concepts has stood the test of time; each gives the designer a foundation for more sophisticated methods, in both traditional and OO development. They help answer: What criteria partition software into components? How is function or data-structure detail separated from a conceptual representation? What uniform criteria define the technical quality of a design? As M. A. Jackson put it, wisdom begins with knowing the difference between getting a program to work and getting it right.

1 · Abstraction Must know

You say "book a train ticket" without listing the forty clicks behind it. A modular solution can be described at many levels of abstraction: at the highest level, in broad terms using the language of the problem environment; at lower levels, in more detail, mixing problem-oriented and implementation-oriented terms; at the lowest level, in a form that can be directly implemented.

Procedural abstraction — a sequence of instructions that have a specific and limited function. The name implies these functions, but specific details are suppressed.

Data abstraction — a named collection of data that describes a data object.

The steps behind open can be replaced (e.g., an automatic door with a sensor) as long as the function implied by the name stays the same — users of the abstraction are unaffected. SafeHome-style example: data abstraction Sensor (type, id, location, threshold) with procedural abstraction armSystem().

Open with Grady Booch: "Abstraction is one of the fundamental ways that we as humans cope with complexity." Then the levels, both types and the door example — a complete 5-mark answer.

2 · Architecture Must know

Software architecture — "the overall structure of the software and the ways in which that structure provides conceptual integrity for a system" (Shaw and Garlan).

In simplest form it is the structure or organization of program components (modules), the manner in which they interact, and the structure of data they use (more broadly, major system elements and their interactions). Think of it as the software's floor plan. The architectural rendering is the framework for detailed design; architectural patterns solve common design problems.

Property to specify (Shaw and Garlan)Meaning
Structural propertiesThe components (modules, objects, filters) and how they are packaged and interact — e.g., objects encapsulate data and processing and interact by invoking methods.
Extra-functional propertiesHow the architecture achieves performance, capacity, reliability, security, adaptability and other characteristics.
Families of related systemsDraw on repeatable patterns found in families of similar systems — the ability to reuse architectural building blocks.

Five kinds of architectural model: structural (an organized collection of program components); framework (repeatable design frameworks of similar applications — higher abstraction); dynamic (behaviour — how structure or configuration changes with external events); process (the business or technical process the system must accommodate); functional (the functional hierarchy). Architectural description languages (ADLs) describe components and how they connect. There is debate whether architecture is derived separately (between requirements engineering and design) or is an integral part of design. Advice: don't let architecture "just happen" — design it explicitly.

Five models — "Some Famous Designers Plan First": Structural, Framework, Dynamic, Process, Functional.

3 · Patterns Important

Design pattern — "a named nugget of insight which conveys the essence of a proven solution to a recurring problem within a certain context amidst competing concerns" (Brad Appleton).

A pattern describes a design structure that solves a particular problem in a specific context and amid "forces" that affect how it is applied. Its description lets the designer decide (1) whether it is applicable to the current work, (2) whether it can be reused (saving design time), and (3) whether it can guide the development of a similar but functionally or structurally different pattern. (Christopher Alexander: a pattern can be used "a million times over, without ever doing it the same way twice".) Everyday example: a traffic roundabout — one named, proven idea for crossing traffic, built differently each time. Software: the Observer pattern — when a SafeHome sensor trips, the display, alarm and dialler that depend on it are all notified.

4 · Separation of concerns Must know

Separation of concerns — any complex problem can be more easily handled if it is subdivided into pieces that can each be solved and/or optimized independently (Dijkstra). A concern is a feature or behaviour specified in the requirements model.

If problem p1 is perceived as more complex than p2, it needs more effort. And the perceived complexity of two problems combined is often greater than the sum of each taken separately:

C(p1) > C(p2) ⇒ E(p1) > E(p2)   and   C(p1 + p2) > C(p1) + C(p2) ⇒ E(p1 + p2) > E(p1) + E(p2)

Hence divide and conquer. Separation of concerns appears in modularity, aspects, functional independence and refinement.

It can be taken too far: split a problem into very many tiny pieces and each is easy, but integration may be very difficult — see the modularity graph (Fig 5.4).

5 · Modularity Must know

Modularity — software is divided into separately named and addressable components, sometimes called modules, that are integrated to satisfy problem requirements. It is the most common manifestation of separation of concerns. "Modularity is the single attribute of software that allows a program to be intellectually manageable" (Myers).

Monolithic software (one large module) cannot be easily grasped — its number of control paths, span of reference, number of variables and overall complexity make understanding close to impossible. So the design is broken into modules — but not indefinitely:

  • Cost/module falls as the number of modules rises (same requirements, more modules ⇒ smaller modules); the cost to integrate rises.
  • The total cost is U-shaped: some number M of modules gives minimum development cost, but we cannot predict M with assurance.
  • So modularize, but stay in the vicinity of M — avoid undermodularity and overmodularity.

Why modularize? Development can be more easily planned; increments can be defined and delivered; changes are easier to accommodate; testing and debugging are more efficient; long-term maintenance has fewer serious side effects.

6 · Information hiding Must know

Modularity raises the question "How do I decompose a solution to obtain the best set of modules?" Parnas answers it:

Information hiding — modules should be "characterized by design decisions that (each) hides from all others": the information (algorithms and data) inside a module is inaccessible to other modules that have no need for it.

Effective modularity comes from independent modules that communicate only the information necessary to achieve software function. Abstraction defines the procedural/informational entities; hiding defines and enforces access constraints to procedural detail and local data structures, which sit behind a module interface.

Benefit: greatest when modifications are needed during testing and maintenance — because most detail is hidden, errors introduced during modification are less likely to propagate to other parts of the software. (Like driving a car through its steering, pedals and gears: the engine can change from petrol to electric and you still drive the same way.)

7 · Functional independence: cohesion and coupling Must know

Functional independence grows directly out of separation of concerns, modularity, abstraction and information hiding (Wirth, Parnas; solidified by Stevens, Myers and Constantine).

Functional independence — achieved by developing modules with "single-minded" function and an "aversion" to excessive interaction with other modules: each module addresses a specific subset of requirements and has a simple interface.

Cohesion — an indication of the relative functional strength of a module (the degree to which it focuses on just one thing).

Coupling — an indication of the relative interdependence among modules (the degree to which a module is connected to other modules and the outside world).

Why independence? Independent modules are easier to develop (function is compartmentalized, interfaces simplified — vital for teams) and easier to maintain and test (secondary effects of changes are limited, error propagation is reduced, and reuse becomes possible). "Functional independence is a key to good design, and design is the key to software quality."

  • Cohesion extends information hiding: a cohesive module performs a single task needing little interaction with others — ideally it does just one thing. Multiple functions are sometimes necessary, but "schizophrenic" modules (many unrelated functions) must be avoided. Aim: high cohesion.
  • Coupling depends on interface complexity, the point at which entry or reference is made to a module, and what data pass across the interface. Aim: lowest possible coupling — simple connectivity is easier to understand and less prone to the "ripple effect" (an error in one place propagating through the system).

MeasuresFunctional strength inside one moduleInterdependence between modules

Co-HE-sion = inside one module; COUPLE-ing = between two. Good design = high cohesion, low coupling — "strong teams, few meetings".

Types of cohesion and coupling (Pressman Ch 10, component-level design)

Chapter 8 only defines the two ideas; their types are listed later in the book. Learn them if your paper asks for "types".

Cohesion typeMeaning (highest level first)
FunctionalShown mainly by operations: the component performs a targeted computation and returns a result.
LayerPackages/components/classes: a higher layer uses services of a lower layer, but lower layers never access higher ones.
CommunicationalAll operations that access the same data are defined within one class.

Coupling categories: content (one component secretly modifies another's internal data — violates information hiding); common (components share a global variable); control (A() passes a control flag that directs B's logic); stamp (ClassB is the type of an argument of a ClassA operation); data (long strings of data arguments are passed); routine call (one operation invokes another); type use (A uses a data type defined in B); inclusion/import (A includes or imports B's package or content); external (communication with infrastructure — OS, database, telecom).

The classic scales (structured design — also widely examined)

Cohesion, worst → best: coincidental (unrelated parts) → logical (similar tasks, one chosen by a flag) → temporal (tasks done at the same time, e.g., start-up) → procedural (steps in a fixed order) → communicational (parts share the same data) → sequential (output of one part feeds the next) → functional (all parts serve one well-defined task).
Coupling, worst → best: content (uses/changes another's internals) → common (shared global data) → external (shared external format, protocol or device) → control (passes a control flag) → stamp (passes a whole data structure when only part is needed) → data (passes only the elementary data needed).

8 · Refinement (stepwise refinement) Must know

Stepwise refinement — a top-down design strategy proposed by Niklaus Wirth: a program is developed by successively refining levels of procedural detail; a macroscopic statement of function (a procedural abstraction) is decomposed step by step until programming-language statements are reached.

Refinement is a process of elaboration: start with a statement of function (or information) at a high level of abstraction that says nothing about internal workings, then add more detail at each successive refinement.

Abstraction and refinement are complementary. Abstraction lets you specify procedure and data internally but suppress the need for "outsiders" to know low-level details; refinement reveals low-level details as design progresses. Together they build the complete design model.

PointAbstractionRefinement
DirectionHides detail — up to the big pictureAdds detail — down towards code
PurposeOutsiders need not know low-level detailsReveals low-level details as design progresses
ResultNamed procedural and data abstractionsA hierarchy of ever more detailed steps

Don't jump straight to full detail and skip refinement steps — it causes errors and omissions and makes the design much harder to review.

9 · Aspects Important

Requirements analysis uncovers concerns — "requirements, use cases, features, data structures, quality-of-service issues, variants, intellectual property boundaries, collaborations, patterns and contracts". Ideally each is isolated, but some concerns span the entire system and cannot easily be compartmentalized.

Crosscutting — requirement A crosscuts requirement B "if a software decomposition [refinement] has been chosen in which B cannot be satisfied without taking A into account."

Aspect — a representation of a crosscutting concern.

Example (SafeHomeAssured.com): requirement A (use case ACS-DCV) lets a registered user view video from cameras placed in a space — design representation A*. Requirement B: a registered user must be validated before using SafeHomeAssured.com — it applies to every function; design representation B*. B* crosscuts A*, so B* is an aspect of the WebApp.

Aspects must be identified so that the design can accommodate them during refinement and modularization. Ideally an aspect is implemented as a separate module (component), not as fragments "scattered" or "tangled" through many components; the architecture should support a mechanism for defining such a module. Typical crosscutting concerns: security, logging, error handling.

10 · Refactoring Must know

Refactoring — "the process of changing a software system in such a way that it does not alter the external behavior of the code [design] yet improves its internal structure" (Fowler).

An important design activity in many agile methods (e.g., Extreme Programming): a reorganization that simplifies the design (or code) of a component without changing its function or behaviour. The design is examined for redundancy, unused design elements, inefficient or unnecessary algorithms, poorly constructed or inappropriate data structures, or any other failure that can be corrected. Result: software that is easier to integrate, test and maintain.

Refinement vs refactoring: refinement adds detail top-down while the design is being created; refactoring is done after a design or code exists — "kind of an optimization pass through the software" — and changes only internal structure. Refactoring does not mean redesigning everything iteratively.

11 · Object-oriented design concepts Important

The chapter names classes and objects, inheritance, messages and polymorphism and explains them in Appendix 2. Coad and Yourdon: object oriented = objects + classification + inheritance + communication.

Class
Encapsulates the data and procedural abstractions describing a real-world entity — a template/blueprint for similar objects.
Object
An instance of a class; it inherits the class's attributes and operations.
Attributes / operations
Attributes describe the class (values from a domain); operations (methods, services) are the algorithms that process the data.
Encapsulation
Data, operations and related information packaged under one name and reused as one component.
Inheritance
A subclass (specialization) inherits all attributes and operations of its superclass (generalization) — reuse is direct; superclass changes propagate down.
Messages
A message, message(<parameters>), stimulates behaviour in the receiving object, which executes an operation.
Polymorphism
Lets different operations have the same name, reducing the effort to extend a design and decoupling objects.

Polymorphism example: a conventional program that draws line graphs, pie charts, histograms and Kiviat diagrams needs control logic (if graphtype = linegraph then DrawLineGraph(data) …), and every new graph type means a new module and edited logic. In OO design each graph is a subclass of Graph with its own draw operation, so the design reduces to draw <graphtype>; a new type is just a new subclass. A new class can be built from scratch, inherit from a class with most of what it needs, inherit after restructuring the hierarchy, or override existing characteristics; misused inheritance (e.g., multiple inheritance) makes designs error-prone.

The class "wall" achieves information hiding; methods working on few attributes raise cohesion; communicating only through methods lowers coupling. OO concepts reinforce concepts 6 and 7.

12 · Design classes Must know

Analysis classes (from the requirements model) describe problem-domain elements that users see, at a high level of abstraction and in business jargon. Design classes (1) refine the analysis classes with the detail needed to implement them and (2) implement a software infrastructure supporting the business solution — with much more technical detail.

Five types: "Under Busy Professors, Pupils Study" (User interface, Business domain, Process, Persistent, System). Well-formed: "Can People Have Lunch?" (Complete & sufficient, Primitiveness, High cohesion, Low coupling).

13 · Dependency inversion Important (8th/9th edition)

In hierarchical architectures, high-level "control" components depend directly on low-level "worker" components, so changing a worker forces changes in the controller — the design is tightly coupled.

Dependency inversion principle — high-level modules (classes) should not depend [directly] upon low-level modules; both should depend on abstractions. Abstractions should not depend on details; details should depend on abstractions.

The newer edition's illustration is a small program that reads keystrokes and prints them: the control module invokes the workers through abstractions (abstract classes). The abstract reader can point to a keyboard's read() in one context and a sensor's in another, so workers can be swapped without touching the controller. This reduces coupling and improves testability.

14 · Design for test Important (8th/9th edition)

There is a chicken-and-egg debate about whether software design or test-case design should come first:

  • In test-driven development (TDD) tests are written before other code and guide the design in short cycles: write a test → it fails → write just enough code → the test passes.
  • If design comes first, it must include seams (also called test hooks) — places in the detailed design where test code can be inserted to probe the state of the running software and to isolate the code under test from its production environment. Seams must be consciously designed at the component level, thinking about the tests each component will need — like building a car with diagnostic ports already fitted.

5.5 The design model Must know

The two dimensions of the design model Must know

The process dimension shows the evolution of the design model as design tasks are executed in the software process. The abstraction dimension shows the level of detail as each analysis-model element is transformed into a design equivalent and refined iteratively. The dashed line is the boundary between the analysis and design models — sometimes clear, sometimes the analysis model slowly blends into the design. Design uses many of the same UML diagrams as analysis, but refined and elaborated with more implementation-specific detail, emphasizing architectural structure and style, components, and interfaces.

The elements on the horizontal axis are not always developed in sequence: preliminary architectural design usually comes first, then interface and component-level design, often in parallel; the deployment model is usually delayed until the design is fully developed. Design patterns can be applied at any point.

To draw it in the exam: two axes (abstraction high→low, process →), four columns, a sloping dashed line with "analysis model" above and "design model" below, and 2–3 diagram names per column with downward arrows.

Data design elements Important

Data design (also called data architecting) builds a model of data/information at a high level of abstraction (the customer's/user's view), then refines it into progressively more implementation-specific representations. The architecture of the data strongly influences the architecture of the software that processes it. Data design matters at every level:

  • Program component level — design of data structures and the algorithms that manipulate them.
  • Application level — translation of the data model into a database, pivotal to the business objectives.
  • Business level — data from disparate databases reorganized into a data warehouse for data mining / knowledge discovery.

Architectural design elements Must know

Equivalent to the floor plan of a house — the layout of rooms, their size, shape and relationships, and the doors and windows that allow movement — architectural elements give an overall view of the software. The architectural model is derived from three sources:

  1. information about the application domain of the software;
  2. specific requirements model elements (e.g., data flow diagrams or analysis classes, their relationships and collaborations);
  3. the availability of architectural styles and patterns.

It is usually drawn as a set of interconnected subsystems, often derived from analysis packages; each subsystem may have its own architecture (e.g., a GUI following a standard UI style).

Interface design elements Must know

Like the detailed drawings for the doors, windows and external utilities of a house (how they operate, how water, power, gas and telephone come in and are distributed, where the doorbell and intercom are), interface elements show how information flows into and out of the system and among the components of the architecture. There are three:

Interface elementKey points
1. User interfaceNow often called usability design. Includes aesthetic elements (layout, colour, graphics, interaction mechanisms), ergonomic elements (information layout and placement, metaphors, UI navigation) and technical elements (UI patterns, reusable components). The UI is usually a unique subsystem of the architecture.
2. External interfacesTo other systems, devices, networks or producers/consumers of information. Need definitive information about the other entity — gathered in requirements engineering and verified when interface design starts (it can change over time). Should include error checking and, if needed, security features.
3. Internal interfacesBetween design components; closely tied to component-level design. Design classes define the operations and messaging schemes for collaboration; each message carries the needed information for the requested operation. In input–process–output design, interfaces come from data flow and processing narratives.

Interface (UML) — "a specifier for the externally-visible [public] operations of a class, component, or other classifier (including subsystems) without specification of internal structure" — simply, a set of operations describing part of a class's behaviour and giving access to them.

In an advanced SafeHome, control-panel functions may be offered through a wireless PDA or mobile phone. ControlPanel implements readKeyStroke() and decodeKey(); to provide them to WirelessPDA and MobilePhone, an interface KeyPad is defined with no attributes, only the keypad operations. In UML this is a realization: part of ControlPanel's behaviour is implemented by realizing KeyPad's operations.

Component-level design elements Must know

Like the detailed drawings of each room (wiring, plumbing, switches, sinks, cabinets, flooring), component-level design fully describes the internal detail of each component: data structures for all local data objects, algorithmic detail for all processing, and an interface giving access to all component operations. In OO work a component is drawn as a UML component diagram (Fig 5.15a): SensorManagement performs all SafeHome sensor functions (monitoring, configuring) and a dashed arrow links it to its assigned class Sensor. Details can be modelled with a UML activity diagram (processing logic), pseudocode or a flowchart/box diagram (procedural flow, following structured programming rules), and data structures in pseudocode or the implementation language.

Deployment-level design elements Important

They show how software functionality and subsystems are allocated within the physical computing environment. SafeHome runs on a home-based PC, the SafeHome control panel and a server at CPI Corp. (Internet access). A UML deployment diagram (Fig 5.15b) shows the subsystems in each node — the PC houses security, surveillance, home management and communication, plus an external access subsystem for all outside access attempts. It begins in descriptor form (environment in general terms — "personal computer" could be a Mac, Windows PC, Sun workstation or Linux box) and is later redrawn in instance form (each specific, named hardware configuration identified) late in design or as construction begins.

Chapter 5 in one page

Core ideas

  • Design model = architecture, data structures, interfaces, components (requirements model = data, function, behaviour).
  • Why design? Quality is fostered here: assessable, the only accurate translation of requirements, foundation for later work; without it the system is unstable.
  • Position: last action of modeling, before construction, in any process model. Begin with data, then architecture.
  • Good design: firmness, commodity, delight; diversification → convergence; iterative, high → low abstraction.

Lists to write word-perfect

  • 3 characteristics: explicit + implicit requirements; readable guide; complete picture (data, function, behaviour).
  • FURPS: Functionality, Usability, Reliability, Performance, Supportability.
  • Methods share: translation mechanism, notation, refinement/partitioning heuristics, quality guidelines.
  • Architecture: structural, extra-functional, families of related systems; models: structural, framework, dynamic, process, functional.
  • Design classes: user interface, business domain, process, persistent, system.
  • Well-formed: complete & sufficient, primitiveness, high cohesion, low coupling (Law of Demeter).
  • Architecture sources: domain, requirements elements, styles & patterns. Interfaces: UI, external, internal.

The concepts in one line each

  • Abstraction: hide detail; procedural (open), data (door).
  • Architecture: overall structure, conceptual integrity.
  • Patterns: proven solution, recurring problem, context.
  • Separation of concerns: divide and conquer.
  • Modularity: named modules; stay near M.
  • Information hiding: modules hide decisions (Parnas).
  • Functional independence: high cohesion, low coupling.
  • Refinement: top-down elaboration (Wirth).
  • Aspects: crosscutting concern in its own module.
  • Refactoring: better structure, same behaviour (Fowler).
  • OO: class, object, inheritance, message, polymorphism.
  • Design classes: 5 types, 4 well-formed traits.
  • Newer: dependency inversion, design for test.

Abstraction vs refinement

Abstraction hides low-level detail from outsiders; refinement reveals it step by step. Complementary.

Cohesion vs coupling

Cohesion = strength inside a module (high). Coupling = dependence between modules (low; no ripple effect).
